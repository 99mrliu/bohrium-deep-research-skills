# 回复信模板与语气规范

letter_build.py 按本模板生成回复信；Agent 润色时不得破坏「每子要求一块」的结构。

## 1. 整体结构

1. **总述**：意见条数、子要求总数、裁决分布（采纳/部分采纳/不采纳）、补做类数量——数字一律取自 `matrix.py stats`，不手写。
2. **逐条回复**：按意见分节；每条意见先摘录原文，再逐子要求成块。
3. **收口两表**：裁决统计表、证据状态表（补做类：状态/出处/无法补做的替代说明）。

## 2. 每个子要求块的必备元素

```
### R1.1（类型 / 严重程度 / 动作）
**子要求摘录**：“<逐字摘录>”
**裁决**：采纳 / 部分采纳 / 不采纳
**理由**：<为什么这样裁决，一句话以上>
**回应**：<具体做了什么 / 解释了什么；禁止空话>
**修改定位**：CHG-xx（§章节，第 N 段）或（无对应 CHG）+ 说明
**证据状态**（仅补做类）：到位/部分到位/无法补做 + 出处 + 替代说明
```

缺任何一个元素，coverage_check 或人工复核都会判「答漏」。

## 3. 语气四档

| 档位 | 适用 | 句式示例（中） | 句式示例（英） |
|---|---|---|---|
| 接受 | 意见合理、已落实 | 「感谢指出。已在 §2 补充……（CHG-03）。」 | "Thank you. We have added ... in §2 (CHG-03)." |
| 澄清 | 意见源于信息不足，补一句说明即可 | 「感谢提问。原文第 X 段实际已说明……；为避免歧义，我们在修订稿中补充了一句……」 | "Thank you. This is stated in §X; to avoid ambiguity we have added ..." |
| 礼貌反驳 | 意见与基线事实冲突或前提有误 | 「感谢该建议。我们的理解是……，依据为基线原文『……』。因此本轮未按此修改，若审稿人有进一步依据我们愿意再议。」 | "We respectfully disagree: the baseline states '...'. We therefore did not make this change, but remain open to further evidence." |
| 申诉 | 涉及结论存废的重大分歧（慎用） | 「该意见涉及核心结论，我们认为……。恳请编辑与审稿人考虑以下依据……」 | "This point affects our main conclusion. We kindly ask the editor and reviewers to consider ..." |

## 4. 禁用语与禁用行为

- 禁用空话：「感谢意见，我们已认真修改」而无定位；「已按要求修改」而无 CHG。
- 禁用攻击/傲慢：「审稿人理解有误」「这显然不对」「众所周知」。
- 禁用过度承诺：「我们将在后续工作中全面验证」（除非 evidence 里确有计划出处）；「保证」「一定」。
- 禁用无原则顺从：明知意见有误仍采纳；或采纳了却不落稿。
- 禁止冒称：真实审稿人逐字要求、真实补做实验、原作者已改稿、编辑部已接收。
- 禁止删块：任何子要求块只能从矩阵重新生成，不得手工从信里删除（coverage_check 会 FAIL）。

## 5. 「无法补做」的标准写法

> **裁决**：部分采纳。
> **理由**：意见合理，但本演练仅提供组织方基线摘要，无原始数据与实验条件，无法真实补做。
> **回应**：我们在修订稿 §X 补充了局限性声明（CHG-xx），明确该验证的缺口；在证据清单中标注为「无法补做」并给出替代依据（如对基线已有数据的重分析结果）。
> **证据状态**：无法补做 ｜ 替代说明：<具体内容>

要点：能做的一半（局限声明、替代分析、文本修订）必须真实落稿，不能只声明缺材料就跳过。
