# 修改记录（change_record）写法指南

改稿不留差异记录是基础 Agent 的典型失败：申请人无法看出改了什么、为何改、哪些仍需自己确认。本 bundle 用 version_diff.py 生成机器可回检的 change_record.md，Agent 负责补充解释。四部分写法：

## 一、变更统计（脚本生成）

新增/删除/修改行数。replace 块内 min(删,增) 计为"修改"。统计必须与文末 unified diff 一致——脚本保证，不要手改数字。

## 二、按小节归组（脚本生成 + Agent 加注）

脚本按最近的 `#` 标题归属每个变更块。Agent 应在交付说明里为每个非空小节补一句**修改理由**，理由只许引用材料或组织方工单，例如："按 organizer-workorder 要求将考核指标并入研究目标"。禁止写"润色""优化表达"这类无信息量理由。

## 三、人工确认项清单（脚本提取 + Agent 维护）

- 来源：母稿中所有 `【待…确认…】` 占位符（含【待申请人确认：…】）。
- 每条以 `- [ ]` 复选框呈现，申请人逐项勾选关闭；关闭后从母稿删除占位符并升版本号。
- 新版已移除而旧版存在的占位符，脚本单独标注"旧版有、新版已移除（请确认是否已解决）"——防止静默吞掉未决问题。

## 四、材料缺口与异常的记录位

修改记录之外，两类信息必须留痕（写入 result.json 的 uncertainty，并在 change_record 交付说明中引用）：

1. **材料缺口**：PDF 无文本层、证据明确缺失的研究基础条目等，以【待申请人确认：…】占位进母稿，同时列入 uncertainty。
2. **异常**：渲染降级（缺 soffice/pdftoppm）、表格降级为段落、不支持的 Markdown 写法等，写明影响面与替代方案。

## 反模式（禁止）

- 只交付新版全文、无任何 diff——申请人无法审查改动。
- 手编"修改摘要"但与实际文本不符——diff 必须机器生成、可复跑。
- 把待确认项直接编成确定事实——占位符只能被申请人确认后移除。
- 记录时间戳/随机 ID 导致复跑字节不一致——version_diff.py 不写时间戳。
