# 预算手册：时间、请求与牺牲的次序

适用预算：约 900 秒墙钟、约 64 次模型请求、单次响应上限 16384 token。以下比例为建议值，应按案例材料规模伸缩；原则不变。

## 1. 阶段分配

| 阶段 | 时间占比 | 请求占比 | 关键动作 |
| --- | --- | --- | --- |
| intake | 0–60 秒（约 7%） | ≤2 次 | 运行 contract_boot.py；核对 intake_manifest 与播种 uncertainty |
| extract | 60–300 秒（约 25%） | 约 16 次 | 通读材料、提取要点与证据；每个来源读毕即 checkpoint --source |
| design | 300–450 秒（约 15%） | 约 8 次 | 设计导图层级；结构方案写入 /app/work |
| build | 450–650 秒（约 30%） | 约 20 次 | 生成产物文件；逐产物 checkpoint --artifact |
| verify | 650–800 秒（约 15%） | 约 10 次 | 填齐契约字段、消解或保留 uncertainty、运行 final_audit 并修复违例 |
| deliver | 800–880 秒（约 8%） | ≤3 次 | 复核 result.json 与 change_record，确认交付状态 |

保留约 20 秒与约 5 次请求作为不可动用的尾部余量，用于最后一次 checkpoint 与 final_audit。

## 2. 何时停止改进、转入收尾

满足以下任一条件即停止一切内容生成，转入收尾（填字段、写限制、对账）：

- 墙钟达到约 650–700 秒；
- 模型请求剩余约 8 次；
- 单次响应 token 接近上限导致输出被截断的风险显现；
- final_audit 的违例项已无法在剩余预算内以真实内容修复。

收尾动作的最小集：一次 checkpoint 写实状态（必要时 --status partial 加 --note 说明缺口）→ final_audit → 交付。诚实的 partial 永远优于虚假的 success。

## 3. 牺牲次序（先牺牲什么）

预算不足时按以下次序放弃，前者先于后者：

1. **预览与表现层**：导图的美化、配色、多格式导出、渲染截图——最先放弃；
2. **证据的广度**：每个论点只保留最强的一条证据，放弃"再多找一条"的加固；
3. **分支深度**：导图第三层以下的细节分支，收缩到第二层；
4. **覆盖率末段**：按重要性排序的次要点——但放弃必须在 uncertainty 中显式声明"哪些要点被略去及原因"；
5. **永不牺牲**：result.json 合法性、case_id 正确性、状态诚实、uncertainty 披露、change_record 完整性、final_audit 的执行。

即："previews before evidence, polish before coverage"——表现先于证据牺牲，打磨先于覆盖牺牲；而诚实层的一切不可牺牲。

## 4. 请求经济学

- 合并读写：一次响应内完成"读材料 + 写中间稿"，避免往返；
- checkpoint 调用廉价（本地脚本，不占模型请求），应频繁使用；模型请求才是稀缺资源；
- 长材料分段读取时，每段处理完立即落盘要点，防止上下文溢出导致重做；
- 任何"再润色一遍"的决定须先核对剩余请求数：不足 10 次时不启动新的生成性请求。
