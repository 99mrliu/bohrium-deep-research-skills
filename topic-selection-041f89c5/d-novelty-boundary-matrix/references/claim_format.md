# claims.json 格式与分类细则

## 格式

```json
{
  "proposal_title": "提案名称",
  "search_boundary": "本判断覆盖 /input 文献集 9 条记录（2015–2026），无联网检索通道",
  "claims": [
    {"id": "C1", "text": "提出了一种新的……", "type": "method"},
    {"id": "C2", "text": "首次将 X 用于 Y", "type": "scenario"}
  ]
}
```

- `id`：C1、C2… 唯一；`text`：尽量保留提案原文，改写时注明；
- `type` ∈ {method, data, scenario, conclusion}；
- `search_boundary`：**必填**。没有边界声明时脚本对所有"未见覆盖"只能判 indeterminate——这是有意设计。

## 四类创新的判定线索

| 类型 | 成立的关键问题 | 易被高估的形式 |
|---|---|---|
| method 方法创新 | 机制/算法/流程本身是否有别于已有方法？ | 换骨干网络、换损失函数权重、模块堆叠 |
| data 数据创新 | 数据/标注/基准是否是新的且可复用？ | 私有小样本、他人数据的子集 |
| scenario 场景迁移 | 方法是否已在该场景被用过？迁移的障碍是否被实质解决？ | "首次应用于"但无场景特异性贡献 |
| conclusion 结论修正 | 是否推翻了已有具体结论且有证据？ | 复述他人局限性分析 |

## 纪律

- 一条陈述只表达一个创新点；复合陈述拆开。
- 类型存疑时选更弱的类别（如 method/scenario 之间选 scenario），并在备忘录说明。
- 提案原文没有的创新点不添加；由评估方归纳的陈述要标注来源。
