# N-version 冗余执行：依据、分歧分类学与收敛流程

## 一、为什么是冗余执行，而不是事后审计

单管道清洗 + 事后审计防得住“管道没按文档跑”的一部分问题，但防不住两类根源性
风险：

1. **实现错误**：审计审的是产物与文档的一致性，而文档读者（含审计者自己）容易
   复现同一个错误的心智模型；同一个人写的实现与审计清单存在共模失效。
2. **规约歧义**：一段自然语言规则（“保留质量较好的重复行”）常有多种合理解读。
   单管道只会无声地选一种，分歧永远不会浮现。

N-version 执行学的做法：同一份**形式化规约**（rules.json），交给两个**结构独立、
不共享代码**的实现分别执行，逐格 diff。两个实现要在同一个错误上“撞车”，概率远
低于单一实现出错；而规约里每一处歧义，几乎必然表现为两引擎在某处分道扬镳——
分歧即发现。

本技能的两个引擎刻意制造结构性差异：

| 维度 | engine_row.py（A） | engine_col.py（B） |
| --- | --- | --- |
| 读取 | csv.reader 逐行流式 | csv.DictReader 全量→dict-of-lists |
| 控制结构 | 命令式循环、严格大于才替换 | 推导式、集合运算、max(tuple key) |
| 分类 | 逐行逐格即时分类 | 逐列整列分类再组装 |
| 平局默认（规约未写 tie 时） | first_occurrence | last_occurrence |

最后一行是刻意的：**相反的文档化默认值**保证规约遗漏平局规则时双跑必分歧，
把歧义逼回规约层面解决，而不是被某一侧的默认悄悄吞掉。

## 二、分歧分类学

reconciliation_queue.csv 中每条分歧按以下三分法判定（判定是 Agent 的工作，
工具只负责把两引擎的值与各自台账理由摆在一起）：

### 1. 规约歧义（spec ambiguity）

两个引擎都忠实地执行了规约，但规约本身允许两种解读。症状：分歧集中在某类语义
决策上，两引擎的 ledger 理由各自自洽。**处置：改 rules.json 把语义写死，双跑。**

典型实例（见 examples/）：规约只写 `keep=most_complete` 而未写 `tie` 时，
caffeine 两行完整度相同，A 依默认取首现（12.5）、B 依默认取末现（13.0）。
修复是在规约补 `"tie": "first_occurrence"`，而不是改任何一侧引擎。

### 2. 引擎缺陷（engine defect）

一侧引擎偏离了规约。症状：一侧的 ledger 理由与规约文字矛盾，或一侧输出内部不
自洽（如把哨兵值计入完整度、对无量纲列做单位换算）。**处置：以另一侧与规约为
参照修出错引擎，双跑。** 修引擎时只改出错侧，禁止“两边一起改到一致为止”——那
会把缺陷磨成共谋。

### 3. 非确定性来源（nondeterminism）

输出本应唯一却因隐状态漂移。常见来源与对策：

| 来源 | 对策（已内置于引擎，复核时照查） |
| --- | --- |
| dict/集合迭代序 | 所有输出前显式排序（ledger 按 src_row/field/record/class；summary 键排序） |
| 浮点格式 | 固定 `.10g`；两引擎做**相同顺序**的算术（先换算后判界） |
| 时间戳/PID/随机数 | 引擎与 verdict 均不写入墙钟时间 |
| 文件系统序 | 不遍历目录取输入；输入文件显式给定 |
| CSV 行尾/引号 | 统一 `lineterminator="\n"`、QUOTE_MINIMAL |

**处置：消除隐状态后双跑；幂等核验（--idempotence）是这类问题的探测器**——
同一引擎同一输入重跑，产物必须字节一致。

## 三、收敛流程

```
        ┌────────────────────────────────────────────┐
        │                                            │
        ▼                                            │
  双跑引擎 A/B → diff_runs → 零分歧？ ──是──→ 幂等核验 ──PASS──→ 放行 /app/output
                        │否                            │FAIL
                        ▼                              ▼
              读 reconciliation_queue.csv        按第三节消除非确定性
              逐条判定分类学类别                       │
                        │                              │
        ┌───────────────┼───────────────┐              │
        ▼               ▼               ▼              │
   规约歧义        引擎缺陷        非确定性 ◄────────────┘
   改 rules.json   改出错侧引擎    消除隐状态
        │               │               │
        └───────┬───────┴───────────────┘
                ▼
        双跑（每一轮都必须双跑，禁止只跑被改侧）
```

收敛纪律：

1. **每一轮都双跑**。只重跑被改的一侧等于回到单管道。
2. **禁止以多数决、平均、任选其一消灭分歧**。两个引擎不是投票者，是两份证词；
   证词冲突时找事实（规约文字、字典出处），不是和稀泥。
3. **修复要落在正确的层**：歧义归规约、缺陷归引擎。把歧义“修”在引擎里（让两侧
   默认一致）会让下一处歧义再次隐形——平局默认值必须保持相反。
4. **无法收敛是合法结局**：多轮后仍有分歧时，status=partial 交付，result.json
   逐条列出未解决分歧（行/字段/两值/两理由/初步判断），reconciliation_queue.csv
   一并交付。诚实 partial 远优于虚假 PASS。
5. **留痕**：每一轮的规约版本、queue、verdict 保留在 /app/work（如
   work/roundN/），最终报告中能讲清“从分歧到收敛”的完整链条。
