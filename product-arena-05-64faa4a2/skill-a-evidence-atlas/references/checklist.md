# 方法与实验章节：六要素写作核查清单与常见失败模式

完稿前逐项核查。每一项都要能回答："依据台账/原文的哪一条（file:line）？"

## 一、方法步骤

- [ ] 步骤顺序与材料中的流程（脚本、日志、README）一致，无臆造环节；
- [ ] 每步的输入/输出对象明确（数据、模型、配置）；
- [ ] 预处理/后处理细节在材料中有出处，缺失则写"材料未提供"。

## 二、实验设置

- [ ] 硬件/环境（GPU、CUDA、框架版本）来自台账 version 类条目或原文；
- [ ] 运行方式（命令、入口脚本）与日志/脚本中的记录一致；
- [ ] 随机种子、确定性设置有出处。

## 三、参数与来源

- [ ] 正文每个数值都带台账 ID（[[Pxxx]]）或 file:line；
- [ ] 超参数名称、取值、单位三者齐全且与台账一致；
- [ ] 冲突参数已按 SKILL.md 第 5 节处置（写明冲突、裁决理由或 [待确认]）。

## 四、数据集与划分

- [ ] 数据集名称、规模、来源（路径/URL）有出处；
- [ ] 划分比例与样本总数**自洽**（见失败模式 3）；
- [ ] 划分方式（随机/按时间/分层）与种子有出处。

## 五、对照实验

- [ ] 基线/消融的设置与材料一致，不虚构对照结果；
- [ ] 指标数值逐一在日志/结果文件中定位；
- [ ] 材料中没有对照实验时，如实说明而非编造。

## 六、可复现性与限制条件

- [ ] 复现所需信息（版本、种子、配置、命令）齐或注明缺口；
- [ ] 材料自身的限制（单种子、单数据集、未报告方差等）如实写出；
- [ ] 不确定性与人工确认项已汇总进 result.json。

## 常见失败模式

1. **"均为默认设置"类无来源断言**——材料未写默认值的参数不得声称
   "默认"。处置：查台账；查不到写"材料未提供"或 `[待确认]`。
2. **配置与日志冲突被静默二选一**——例如 config.yaml 写 lr=0.0003 而
   train.log 显示 lr=0.001。处置：台账 conflicts 已列出；正文写明冲突
   及 file:line，给出裁决理由或列人工确认项。
3. **划分比例与总数不自洽**——如 8:1:1 划分却给出不能整分的总数，
   或比例之和不为 1。处置：用台账中的比例与总数交叉验算，不自洽即
   标 `[待确认]`。
4. **版本号张冠李戴**——把依赖的间接版本写成主框架版本，或把代码
   仓库版本写成数据集版本。处置：以 version 类台账条目的原文行为准。
5. **指标精度幻觉**——日志只有 0.873，正文写 87.32%。处置：数值必须
   与来源逐位一致（百分比换算允许，但不得增添来源没有的位数）。
6. **把草稿中的旧数值带入终稿**——待修草稿本身可能含编造或过期数值。
   处置：终稿以台账为准重填，草稿仅作结构参考；用 ledger_check 兜底。
7. **单位错配**——ms 写成 s、MiB 写成 MB。处置：单位以台账 unit 字段
   与原文为准，换算须注明。
8. **把"未解析文件"当不存在**——PDF/权重文件虽未解析，但可能含关键
   事实。处置：在人工确认项中列出未解析文件清单，说明覆盖缺口。
