# repro-runbook：以可复现性为终极检验的方法与实验章节写作

## 用途

方法章节的终极检验是"读者能否照做复现"。本 Skill 将"方法与实验"章节组织为一份可执行
runbook，面向科研案例写作任务（输入为配置、日志、代码、草稿、PDF 摘录等材料）。其核心动作：

1. **挖掘**：从脚本、日志、README、Makefile、依赖文件、Python 源码中提取真实命令行
   （含多行续行拼接）、运行环境（硬件、CUDA/框架/Python 版本）、随机种子、数据获取方式
   与依赖声明，每条线索绑定 `file:line` 来源；
2. **重排**：把方法步骤组织为"输入 → 命令/操作 → 预期输出 → 判断条件"的可执行步骤表，
   每步绑定材料来源，并按日志时间线给出建议顺序；
3. **清单**：生成复现清单（代码版本、环境、依赖、命令、数据获取、种子、预期校验七项）
   并逐项标注 已给/缺失/材料不可得；
4. **核验**：比对章节中的命令与材料中的真实命令（防止凭记忆改写 flag），核验步骤顺序与
   日志时间线的一致性，不一致即 FAIL，必须修复后方可定稿。

设计原则：脚本只提取、比对与报告，绝不臆造；凡材料缺失的信息，一律在章节中如实标注
缺口并列入人工确认项，而不是编造版本号、种子或命令。编造的细节比坦白的缺口更损害
章节的可信度。

### 三个脚本的分工

| 脚本 | 职责 | 不做什么 |
|---|---|---|
| `scripts/command_mine.py` | 静态扫描材料，产出事实底账 commands.json/md | 不执行任何命令，不推测语义 |
| `scripts/step_table.py` | 产出步骤表骨架 steps.md 与顺序建议 | 不补判断条件，不改正文 |
| `scripts/repro_check.py` | 核验清单、命令一致性、顺序一致性 | 不修改章节，只报告 |

## 运行时契约（必须遵守）

1. **先读输入**：开工前必须读取 `/input/case.json` 与 `/input/task.md` 的实际内容，确认
   `case_id`、`output_contract` 要求的全部字段、章节范围与材料清单；不得假设输入格式。
2. **工作目录**：中间产物（commands.json、steps.md、repro_report 等）一律写入 `/app/work`；
   最终产物写入 `/app/output`。
3. **result.json**：在 `/app/output/result.json` 中给出 `case_id` 以及 `output_contract`
   声明的**全部字段**；字段缺失视为任务失败，不得省略。装配后逐字段对照契约复核一遍。
4. **诚实状态**：任务完成度如实申报；任何一部分未能完成时，状态置为 `partial` 并在
   result.json 中说明哪些字段/章节未完成及原因。不得把未完成谎报为完成。
5. **尽早保存**：每完成一个里程碑（挖掘完成、步骤表完成、正文初稿、核验通过）立即落盘
   当前成果，避免预算耗尽时无产物可交。
6. **来源定位**：章节中的每条命令、参数、版本、种子、数据路径，必须能在材料中定位到
   `file:line`；定位不到的内容不得写成事实，只能写为"材料未提供"并列入人工确认项。
7. **修改记录**：若任务要求基于既有草稿修改，须在产物中保留修改记录（改前/改后/依据），
   例如"draft 将 `--lr 2e-5` 误写为 `--lr 2e-4`，已依据 pipeline.sh:12 改正"。
8. **不确定性**：对推测性内容（如无法从日志确认的步骤顺序、被跳过的不可读文件）显式
   标注不确定性及其影响。
9. **人工确认项**：材料缺口（无种子、无版本、无数据链接等）汇总为人工确认项清单，
   写入章节末尾与 result.json。
10. **六要素覆盖**：章节必须覆盖——步骤、实验设置、参数与来源、数据集与划分、对照
    （baseline/消融）、复现与限制。任一要素材料不足时，写明缺口而非跳过或编造。
11. **预算意识**：总预算 64 次模型请求、900 秒。脚本调用走 shell，不消耗模型请求；模型
    请求优先用于判断条件补全、正文撰写与核验结果修复，避免在逐字抄录类工作上浪费请求。

## 六要素在 runbook 框架下的落位

1. **步骤**：即步骤表（②生成、③补全）。每步"输入→命令→输出→判断条件"四元组齐全，
   顺序有日志依据或显式的不确定性标注。
2. **实验设置**：即环境矩阵（硬件、CUDA、框架、Python、关键库、代码版本），取值全部
   来自 commands.json 的 env 线索并标注来源。
3. **参数与来源**：命令中的每个 flag 即参数记录；正文复述参数时标注 `file:line`。
   材料未出现的参数不得出现在正文中。
4. **数据集与划分**：来自 data 线索（下载命令、数据路径、日志中的规模记录）。划分方式
   材料未说明时，写"材料未说明数据划分"并列入人工确认项，不得假设"常规划分"。
5. **对照**：baseline/消融记录若存在于材料（如对照日志行、对比表格），如实转写并定位
   来源；材料没有对照实验时，明确写"材料未包含对照实验记录"，不得虚构对比数字。
6. **复现与限制**：即复现清单 G1–G7 + 判断条件汇总 + 限制与不确定性一节；清单状态必须
   与 repro_report 一致。

## 模型请求预算分配建议

- 读输入与材料概览：2–4 次；
- 补全判断条件：1–2 次（可一次性对整个步骤表操作）；
- 正文撰写：2–4 次（按章节规模）；
- 核验后修复：每次 FAIL 预留 1–2 次，最多迭代 3 轮；
- 装配与复核 result.json：1–2 次。
- 任何"逐字抄录"类工作都不要用模型请求完成——直接引用脚本产物。

## 调用步骤

设材料已复制到 `/app/work/case/`（PDF 请先转为文本后放入该目录）。

### ① 挖掘命令与环境

```bash
python3 /skills/weekly-skill/scripts/command_mine.py --case /app/work/case --out /app/work
```

产物 `/app/work/commands.json` 与 `commands.md`：每条线索含 `type`
（command/env/seed/data/dep）、`text`、`file:line` 来源、日志时间戳（若有）。
先通读 `commands.md`，建立"材料里到底发生了什么"的事实底账；后续正文中的任何命令、
版本、种子只允许引用此底账。若某条线索可疑（如日志与脚本 flag 不一致），此时记录，
留待④核验后与人工确认项一并处理。

### ② 生成步骤表骨架

```bash
python3 /skills/weekly-skill/scripts/step_table.py \
    --commands /app/work/commands.json --out /app/work/steps.md
```

产物 `steps.md`：列为 步骤号 | 名称 | 输入 | 命令/操作 | 预期输出 | 判断条件（待补）| 来源。
若有带时间戳的日志，步骤按日志时间线排序，且每步标注对应日志时间；无法确定顺序时脚本
诚实标注"顺序待人工确认"，此时必须在章节中注明该不确定性，不得虚构顺序依据。脚本还会
列出"日志中出现但脚本中找不到"以及"脚本中有但日志未执行"的命令，二者都须人工核对。

### ③ 模型补全判断条件与正文

逐行补全步骤表的"判断条件"列：必须可观察、可判定——退出码为 0、产物文件存在、日志出现
特定完成标记、指标不低于某阈值等，并标注依据的材料来源（如 `run.log:8` 的
`eval done: test acc=0.879`）。写法范例见 `references/runbook_format.md` 第 3 节。

随后按 `references/runbook_format.md` 撰写章节正文：实验设置（环境矩阵）→ 数据 →
方法步骤（步骤表 + 叙述）→ 对照设置 → 复现清单与预期校验 → 限制与不确定性 →
人工确认项。硬性纪律：

- 正文命令**逐字照抄**步骤表，不得改写、增删任何 flag，不得把多条命令压成一句；
- 参数取值必须标注来源（`file:line`）；
- 版本写全（如 torch 2.1.0+cu121、CUDA 12.1、Python 3.10.12），禁止 "latest/最新版"；
- 材料没有的信息（种子、划分、对照）写缺口，不编造。

### ④ 核验

```bash
python3 /skills/weekly-skill/scripts/repro_check.py \
    --chapter /app/work/chapter.md \
    --commands /app/work/commands.json \
    --steps /app/work/steps.md \
    --out /app/work
```

产物 `repro_report.json/md`，包含三部分：

- **复现清单 G1–G7**：代码版本、运行环境、依赖、完整命令、数据获取、随机种子、预期校验，
  逐项给出 present / missing / unknown（unknown = 材料本身没有该信息）；
- **命令一致性**：从章节的代码块、行内代码与散文中提取命令，与真实命令逐条比对 flag；
  flag 值被改写（`flag_value_mismatch`）或臆造（`flag_invented`）→ FAIL；
  省略 flag（`flag_omitted`）与多步压一句（`steps_compressed`）→ WARN；
- **顺序一致性**：章节命令顺序与日志时间线比对，矛盾（`order_conflict`）→ FAIL；
  无日志时如实报告 skipped。

**出现 FAIL 必须回到③修复后重新核验**；missing 缺口要在章节中如实说明并列入人工确认项；
unknown 禁止编造补齐。常见失败模式与对策见 `references/repro_failures.md`。

### ⑤ 装配 result.json

按 `/input/case.json` 的 `output_contract` 装配 `/app/output/result.json`：填入 `case_id`
与契约要求的全部字段（章节正文、复现清单、人工确认项等，以实际契约为准），附诚实状态
（完成 / `partial` + 原因）、来源定位表、修改记录、不确定性说明。把 `repro_report.md`
一并复制到 `/app/output/` 作为核验佐证。最后通读 result.json，逐字段对照契约确认无遗漏。

## 异常处理

- **材料中无任何命令线索**：commands.json 为空时，step_table 与 repro_check 不会崩溃，
  会在产物中明确标注；此时章节改为"方法描述 + 缺口声明"，写明"材料未提供可执行命令"，
  并把命令、环境、种子全部列入人工确认项，状态考虑 `partial`。
- **无时间戳日志**：步骤顺序降级为文件出现顺序并显式标注"顺序待人工确认"；repro_check
  的顺序核验自动跳过（skipped），在章节的不确定性一节写明。
- **日志命令与脚本命令对不上**：step_table 会列出未匹配的日志命令；以日志中实际执行的
  命令为准，同时把矛盾点写入人工确认项，不得擅自二选一后隐去另一版本。
- **材料文件不可读/编码异常**：command_mine 跳过该文件并打印 WARN，不中断；在不确定性
  说明中记录被跳过的文件名与原因。
- **PDF 材料**：脚本不解析 PDF；先用可用工具提取文本存为 `.txt/.md` 再放入材料目录，
  并在来源定位中注明"由 PDF 转录"。
- **核验 FAIL 但材料本身矛盾**（如两个脚本 flag 不一致、README 与日志版本冲突）：
  以日志中实际执行的命令/版本为准，在章节与人工确认项中同时记录矛盾双方与来源。
- **章节文件位于材料目录内**：repro_check 会自动排除"以章节自身为来源"的线索，防止
  章节用自己的话自我证明；无需额外处理。
- **预算将尽**：立即停止润色，把已核验的部分与缺口清单写入 result.json（状态 `partial`），
  保证产物完整可交。

## 合成最小示例

`examples/` 内含合成示例（**合成示例，非正式案例结果**）：`examples/case/` 有三条命令的
`pipeline.sh`（含多行续行）、带时间戳且顺序一致的 `run.log`、故意缺种子的 `README.md`、
依赖文件 `requirements.txt`，以及故意把一个 flag 写错（`--lr 2e-5` → `--lr 2e-4`）、省略
`--seed 42`、并把两条命令压成一句的 `draft.md`。一键运行：

```bash
bash examples/run_example.sh
```

产物落在 `examples/expected/`：commands.json/md、steps.md、repro_report.json/md。
预期：command_mine 提取的命令 flag 完整（含续行拼接）；step_table 按日志时间线给出
预处理→训练→评估顺序；repro_check 对缺陷草稿返回 FAIL（抓出 `--lr 2e-4` 的改写），
报告 G6 种子缺失与 G2/G4 等缺口，并对"多步压一句"与省略 `--seed 42` 给出 WARN。

## 边界

- 脚本为纯标准库、确定性、无网络；不执行材料中的任何命令，只做静态提取与比对。
- 命令识别面向常见形态（.sh/Makefile/README 围栏代码块/带 `$` 前缀与时间戳的日志行、
  Python 源码中的种子设置、requirements/environment 依赖文件）；非常规编排（如
  Snakemake、CI YAML 的复杂插值、Shell 函数内动态拼参）可能漏提取，须人工补录后再核验。
- 一致性核验是文本级比对，不理解语义：它能发现 flag 改写、flag 臆造与顺序矛盾，不能
  判断参数取值在科学上是否合理——这属于模型在③中的职责。
- 判断条件、六要素正文、对照实验描述由模型撰写；脚本只提供骨架与事实底账。
- 种子/版本的"材料不可得"是合法结论：如实标注缺口优于编造。
