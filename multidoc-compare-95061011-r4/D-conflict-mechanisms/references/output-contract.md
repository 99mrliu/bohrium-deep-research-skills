# Dynamic output contract

The assembler accepts an output contract in either the workorder (preferred) or case file. It never assumes a fixed shape and always preserves the original value at `result.output_contract`.

## List form

```json
{
  "output_contract": ["summary", "artifacts", "sources", "uncertainty", "change_records"]
}
```

Strings with artifact suffixes (`.md`, `.txt`, `.csv`, `.json`, `.jsonl`, `.html`) are treated as requested artifacts; other strings are requested result fields.

## Dictionary form

```json
{
  "output_contract": {
    "artifacts": ["comparison-matrix.md", "conflict-atlas.md", "result.json"],
    "result_fields": ["case_id", "status", "summary", "sources", "uncertainty", "change_records"]
  }
}
```

`files`, `deliverables`, and `outputs` are artifact aliases. `fields`, `required_fields`, and `result_fields` are field aliases. Nested `result`, JSON-Schema-like `properties`, and `required` containers are also read. A field descriptor may provide `default`; otherwise unknown fields become `unreported`, add an uncertainty, and make the run `partial`. Top-level custom keys are treated as requested result fields rather than silently discarded. This makes preservation robust for both list and dictionary contracts.

Always present: exact `case_id`, `status`, `summary`, `artifacts`, `sources`, `uncertainty`, `change_records`, and the unchanged `output_contract`. Standard aliases such as `comparison_matrix`, `conflict_atlas`, and `integrated_response` point to generated artifacts. Requested artifacts are checked for existence. No requested item is silently dropped.

The three named outputs from the example contract are always generated by the pipeline even for a different contract: `comparison-matrix.md`, `conflict-atlas.md`, and `result.json` (plus `integrated-response.md`). If a contract requests an additional artifact that the pipeline does not know how to generate, status is honestly `partial` and the issue is recorded.
