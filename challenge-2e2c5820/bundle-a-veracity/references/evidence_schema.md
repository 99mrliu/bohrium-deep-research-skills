# 证据台账（evidence.jsonl）模式说明

> 合成示例与正式案例均适用本模式。本文件是 verify_anchors.py 校验规则的人类可读版本。

## 1. 文件格式

每行一个 JSON 对象（JSONL），UTF-8 编码。字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `item_id` | string | 是 | 条目编号，建议 `E01`、`E02` … |
| `category` | string | 是 | 七类之一：`假设与变量` / `对照组` / `设备材料` / `时间成本` / `参数范围` / `风险与异常` / `伦理与安全` |
| `plan_id` | string | 是 | 必须存在于 plans.json 中 |
| `status` | string | 是 | 五值之一：`pass` / `fail` / `missing` / `unknown` / `not_applicable` |
| `quote` | string | 是 | **方案文本的逐字引文**（精确子串，含全角标点），≤120 字符 |
| `basis` | string | 是 | 判定依据类别（见 §4 词表） |
| `note` | string | 是 | 判定说明，可为空串但建议写明推理 |
| `absence_scope` | string | 条件必填 | 当且仅当 `status=missing` 时必须非空（见 §3） |

## 2. 五种状态语义

- **pass**：方案中写明该要素，且与合同/参数域/规范一致。
- **fail**：方案中写明该要素，但与合同、参数域、SOP 或方案自身其他章节**冲突**。
- **missing**：方案**未写明**该要素。
- **unknown**：方案有所表述，但现有材料不足以判定真伪或一致性（例如价格与合同口径不明）。
- **not_applicable**：该要素对本方案不适用，须在 note 中说明理由。

## 3. 铁律与 absence_scope 写法

> **铁律：方案未写明 ≠ 方案已满足。** 凡方案未写明的门槛要素，一律记 `missing`，
> 并在门槛核算时**按未满足计入**，不得以"应该会有""通常如此"放行。

`missing` 条目同样要求 `quote` 锚定：引文应取自**缺失内容本应出现的位置**（如临床样本描述句、
文档标题），作为"检索落点"；`absence_scope` 必须写清检索范围，推荐格式：

> "已逐节检索 v1 第 1–8 节（全文共 N 行），检索词：伦理 / 知情同意 / IRB / 审批，未见任何相关表述。"

即：检索对象（哪份方案、哪些章节）+ 检索方式（关键词或逐节通读）+ 结论。范围越窄，结论越弱；
若只检索了部分章节，必须如实写明，并在 uncertainty 中登记。

## 4. basis 依据词表

`basis` 字段从下列词表中选取（可多值，用 `+` 连接，如 `合同+计算`）：

- `SOP`：标准操作规程、实验室规范
- `设备手册`：仪器说明书、技术规格
- `伦理规范`：伦理审查办法、知情同意要求
- `合同`：组织方提供的资源/价格/预约合同
- `文献`：同行评议论文、预印本
- `计算`：由方案参数与合同价格推算的算术验证

## 5. 引文质量要求

1. **逐字**：quote 必须能用字符串 `find` 在方案文本中命中，一字不差（含空格与全角标点）。
   不要凭记忆转写；从 plans.json 的 text 字段复制。
2. **够短**：≤120 字符，只取能支撑判定的最小片段。
3. **可定位**：verify_anchors.py 会计算 char 起止与行号；被拒条目（exit 2）必须修复后重跑，
   不得绕过。
