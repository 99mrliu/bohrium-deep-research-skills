# 四状态分类与核验规则（match / booking / samples 的判定依据）

本文件是 `scripts/match_resources.py`、`scripts/check_booking.py`、
`scripts/check_samples.py` 的唯一判定依据。脚本行为与本文件冲突时以本文件为准并修正脚本。

## 1. 五档分类定义

| 状态 | 定义 | 必要条件 |
|---|---|---|
| 已具备 | 实验室现有资源即可满足 | 名称归一匹配库存行，且需求给出的每一项规格都通过兼容性比较（含数量），无一项不可比较 |
| 可外协 | 库存不满足/无此项，但外协服务合同覆盖 | 名称归一匹配外协（supplier/service）合同行；记录供应商、单价、货期 |
| 需采购 | 库存与外协都不覆盖，但采购/报价合同覆盖 | 名称归一匹配采购合同行；记录供应商、单价、lead_time_days、order_by |
| 不具备 | 库存无此项或规格明确不兼容，且无任何合同覆盖 | 库存清单存在且可检索；规格失败的具体比较过程必须写入 reason |
| 无法核验 | 证据不足，无法判定 | 案例未提供库存清单、库存行缺少被要求的规格字段、或非数值规格不可比较。**绝不自动通过，绝不猜** |

匹配顺序固定：库存 → 外协合同 → 采购合同 → 不具备。前一档成立即停，但库存
"名称命中而规格不兼容"时不直接判 不具备，而是带着失败原因继续尝试外协/采购
（例如可外购更高规格的设备机时），全部落空才判 不具备。

## 2. 规格兼容性比较规则（按属性类型）

| 属性类型 | 例子 | 判定 |
|---|---|---|
| 能力上限型 | max_rpm、max_flow、capacity、volume、channels、温控上限 | 库存值 **≥** 需求值 |
| 下限/精度型 | min_temperature_c、precision、tolerance、resolution、detection_limit | 库存值 **≤** 需求值（库存能达到更极端/更精细） |
| 数量型（物料） | quantity | 库存可用量 ≥ 需求量，余量 = 库存 − 需求 显式写出 |
| 非数值型 | 型号、颜色、接口 | 归一后字符串相等才通过；不相等或无法比较 → 该项 **无法核验** |

- 需求侧规格为 `null`：视为"未指定"，跳过该项比较（不代表已核验），并遵守
  抽取诚实规则——未知规格只能是 null，不得猜测。
- 库存侧缺少需求指定的规格字段：该项 **无法核验**，进而整条目 无法核验。
- 数值解析：取字段值的前导数值（支持 "15000 rpm"、"-80" 等写法），单位一致性
  由抽取阶段保证；解析失败 → 无法核验。

## 3. 预订排期核验

- 区间表示：ISO 日期（`YYYY-MM-DD`）或 `YYYY-MM-DDTHH:MM`；半开区间 `[start, end)`。
- 重叠判定：`overlap_days = (min(endA, endB) − max(startA, startB)).days`，
  `> 0` 即冲突；`overlap_hours = overlap_days × 24`。冲突表必须列出
  （资源, 窗口A, 窗口B, overlap_hours, 既有预订行）。
- 相对天数：需求只给 `start_day/end_day` 时，用案例提供的 `start_date` 作基准换算；
  基准缺失 → 该项 无法核验 并记 uncertainty。
- 货期核验：`arrival = order_by + lead_time_days`；`slack_days = (needed_by − arrival).days`；
  `slack_days ≥ 0` → 赶得上，`< 0` → 赶不上（写出缺口天数）。任一日期缺失 → 无法核验。

## 4. 样本核验

- 来源：需求给出 source 时与台账比对，归一相等才通过。
- 数量：`台账可用 − 需求 = 余量 ≥ 0`，减法显式写出。
- 存储：台账存储温度须 **≤** 需求温度（如台账 −20°C vs 需求 −80°C → **失败**）。
- 伦理：`ethics_status ∈ {approved, pending, none}`。`pending` / `none` / 任何未知值
  → 阻断性确认项（confirmation item），**绝不视为已批准**；它不一定推翻版本，
  但必须进入 blocking_items 与 conditions_list。

## 5. 平局裁决（多份合同命中同一需求）

1. 单价（unit_price）最低者优先；
2. 单价相同再取 lead_time_days 最短者；
3. 仍相同取列表中第一份，并在 reason 注明。

## 6. 版本级结论（gating 规则）

- 任一 **gating=true** 条目为 不具备 或 无法核验 ⇒ 该版本 **不可行（或需改方案）**。
- 任一采购项货期 **赶不上** needed_by ⇒ 该版本 **不可行（或需改方案）**。
- 任一预订窗口与既有预订 **冲突** ⇒ 该版本 **不可行（或需改方案）**（须调整窗口或换资源）。
- 任一样本 **不满足/不具备** ⇒ 不可行（或需改方案）；样本 **待确认（伦理）** 不计技术
  失败，但计入阻断性确认项。
- 无上述问题但存在 需采购/可外协 项或伦理确认项 ⇒ **有条件可行**，条件清单必须写明：
  下单日与货期、外协单位、需要调整的预订动作、伦理确认动作。
- 全部 已具备 且无冲突 ⇒ **可行**。
